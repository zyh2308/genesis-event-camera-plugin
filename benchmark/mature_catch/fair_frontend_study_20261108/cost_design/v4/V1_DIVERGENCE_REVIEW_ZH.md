# v1 首次服务器 smoke 的轨迹分歧审查

## 已核实的事实

取自实际 g1 `020/021/023/025` 队列回执，而非推测：v1 Ours/25 legacy 在固定轨迹检查处退出，未产生可用于论文的成本点。前 3 步的物理位置最大误差分别为 9.15e-15、2.57e-13、3.50e-13；对应速度误差最高 2.91e-12。第 4 步（0.12→0.16 s）位置误差增至 1.17e-5、速度误差 0.00311，按原门槛正确拒绝。

实际失败运行与参考运行的 `adapter_audit.json` **整个 JSON 相同**，包含 combined 摩擦和子步设置；RGB-D 初始化也整个 JSON 相同，前 4 次状态估计逐项相同。参考第 1 步已经使用非零动作。因此不支持“初始球/材质/seed 不一致”“前三步都是空动作”这两种解释。

动作恢复使用原 `action2dict` AST，与原 runner 相同的三组缩放值。原 `act_inference` 返回网络 `mu`；已检查的原模型实现为拼接浮点网络输出，没有先分配默认双精度输出容器。因此目前没有证据支持将 replay dtype 盲目改成双精度。

## 还没有被归档物理状态覆盖的内部状态

原 `_get_ctrl` 每个 2 ms 步调用 `np.random.normal(1, k_act, 30)`。另外，`move_ee_pose` 使用独立的 `data_arm` 做 IK，并将上次 IK 解写回这一内部模型；它不等于 Genesis 公共 qpos。IK 使用 quadprog、误差停止阈值和关节限制分支。跨机器的细微数值差、内部 IK 状态和随机执行序列都可能影响后续分支，但当前没有证据指定其中哪一个导致本次分歧。独立审查还发现已检查的原配置动作缓冲长度候选均为 `[1]`，不能凭“第4步”断言发生了三步延迟。

## v2 的最小变化

没有修改动作、初始化、物理、核心、权重、容差或测量时窗。只在计时前的预热区新增只读诊断：

- 原 runner 本次实际产生的动作字典，与归档动作解码结果的 dtype 和逐组最大差；
- NumPy RNG 状态的 SHA256、PID/执行噪声参数和缓冲长度；
- 独立 `data_arm.qpos` 及臂/手/底盘目标；
- 若失败，保留实际/参考 qpos、qvel 全向量和最大差的索引。

新增 CPU 合约检查证明读取这些诊断不会推进 RNG、不改动作。正式时窗不增加这些预热诊断。v1 服务器目录保持原样，v2 使用新 instrumentation 目录。

若 v2 显示同一动作和初始化仍无法在当前硬件复现旧轨迹，成本工作应改成固定真实物理状态序列的**采集＋生成＋前端**计时、将共同物理运行成本单列。该边界下不再声称测到了同旧轨迹完全一致的端到端闭环 wall；也不通过放宽物理误差假装原成本合同通过。
